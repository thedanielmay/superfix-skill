## (a) Summary for Daniel
### What you will see on an issue (private repos)
- **A picture of each problem you can see on a screen.** A red box numbered like the problem (1 for P1), with a one-line caption that says the whole thing in words, so the caption alone is enough.
  - All pictures go in the issue description under that problem. The decision comment shows the first picture of each problem below the questions.
  - Problems with no screen (a command, a test, a server) keep their proof as text, as today. No pictures of terminal text.
- **One side-by-side picture per problem in the final comment**, labelled Before and After inside the image and in the caption. The separate before and after files stay in the description.
- **Every comment with pictures has one line:** "Pictures show on the website, not in the GitHub app: <issue link>". You found the app does not show them; the website does. The two-line callout never depends on a picture.
- **A deeper description:** a one-line contents list at the top; per problem, plain words first, then evidence and pictures, then the cause as numbered steps; options with good points, costs and risks; a new "Proposed solution" walk-through with what will look different, what could go wrong and what stays untested. Scaled by size, so a one-line fix stays short.
- **The final comment adds** an estimated cost in USD and one undo line ("To undo: close PR <link> without merging").
- **Public repos get no pictures in 1.4.0.** The decision comment names the folder on your Mac where they are, and Not tested says why.

## (b) Design decisions, with reasons
### D1. Scope
- **In 1.4.0:** before and after pictures (private repos only), the deeper write-up, and every safety fix from the panel.
- **1.4.1:** labels, diagrams, private gap notes (section (j)). **Later:** full Qik publish and restore, SKILL.md trim, opencode test.

### D2. When a picture is taken
- Only for a problem the owner can see on a screen: a page, a rendered component, a Qik draft page. Command, test, log and backend output stays text; no images of terminal text, because text can be searched and checked by the redaction grep and a picture of it cannot.
- **Before** pictures: end of Phase 1, after the failing check. **After** pictures: during solved-check run 2, on the branch, same page and size.
- **Marks:** 3px box with a white outer edge; a numbered label in clear space beside it. Before red `#e00`, after green `#080`, same number; a second mark on P1 is "1b". The caption names the colour and number, so colour is never the only signal.
- **Cap:** 2 pictures per problem per stage, 6 per issue. Simple: 1 before, 1 after per problem.
- **Size:** viewport 1280 by 800 or the area round the target, never a long full page; at most 1600 px wide, metadata stripped, under 1 MB.
- **Names:** `sf-<N>-p<k>-before-<i>.png`, `sf-<N>-p<k>-after-<i>.png`, `sf-<N>-p<k>-before-after.png`. File-mode runs use the journal slug instead of `<N>`.
- **Captions carry the meaning:** the alt text and the caption line say what is wrong (or fixed) and where, in full words. Read on its own, the comment must say everything the picture shows.

### D3. Which browser, and how a run finds out
- **Script path first** (`BROWSER-SCRIPT <python>`): a capture script written by the run into its run folder. It reads the exact secrets from `~/.superfix/runs/<key>/secrets` inside the script, so a secret never enters a tool input. It serves a folder itself in a thread when needed (no background process).
- **MCP path** (`BROWSER-MCP`): Playwright MCP `browser_run_code`, **only when the exact-string check prints NO-LIST** (no credential given this run), because the MCP path cannot read the secrets file without pasting it into a tool call. Its "Viewed" line stays a self-report and the AI detail says so.
- **Claude in Chrome** is never a picture source: it is Daniel's real, signed-in browser. It stays a diagnosis aid, as in 1.3.1.
- **Finding out what the run has:** tools may be listed in full, listed by name only as deferred (load them with ToolSearch `select:<names>` first), or absent. In a `claude -p` nested session the set can differ from the interactive one. The run writes what it found in `Tools used:`, for example `Playwright MCP: deferred, loaded` or `Playwright MCP: absent`.
- **Shell probe** (replaces the shebang trick): try named interpreters, then prove a browser launches:
  `for p in python3 /usr/bin/python3; do command -v "$p" >/dev/null 2>&1 && "$p" -c 'from playwright.sync_api import sync_playwright as s; b=s().start().chromium.launch(); b.close()' >/dev/null 2>&1 && { echo "BROWSER-SCRIPT $p"; break; }; done; echo PROBE-DONE`
  No `BROWSER-SCRIPT` line before `PROBE-DONE`, and no usable MCP: `NO-BROWSER`.
- **A project's own dev server** (for example `npm run dev`), when the page needs one: start it with `nohup`, save `$!` to `~/.superfix/runs/<key>/server.pid`, stop it with `kill "$(cat <that file>)"`; never `pkill -f`.

### D4. Picture safety (every step mechanical where possible)
1. **Private only.** `gh repo view <o>/<r> --json visibility -q .visibility` must print `PRIVATE`. Anything else: nothing is uploaded, ever, in 1.4.0.
2. **Blank exact strings before capture (script path):** every text node, input and textarea value, and the `placeholder`, `title`, `alt` and `aria-label` attributes containing a secret from the list become `[redacted]`. Then the 1.3.1 token patterns and e-mail addresses are blanked the same way.
3. **Regions blanking cannot reach make the picture BLOCKED:** `canvas`, `img`, `video`, `svg image`, a cross-origin `iframe`, a closed shadow root. If any is inside the capture area the script prints `UNREACHABLE <kinds>` and saves nothing. The run then hides that element (`visibility:hidden`) or clips it out and tries again; if the target itself is such a region, no picture, and a Not tested line.
4. **OCR on every saved image,** each to its own file `ocr-<name>.txt`, then: the 1.3.1 exact-string check; the script's fuzzy check (every 8-character piece of each secret, spaces removed, so one misread character does not pass); the 1.3.1 pattern check plus e-mail. **A pattern hit in a picture blocks** (no "you decide" for pictures).
5. **Viewed field from the image:** the script chooses the label side (right, left or below, whichever has room) and stores it in `mark-<name>.side`, which it never prints and the run must not read. The run Reads the PNG and writes `Viewed: label <n> <colour>, <side> of <target>` into `<name>.viewed`. The upload gate compares the two and prints `VIEW-MATCH` or `VIEW-MISMATCH`.
6. **One upload command per file** runs every check above on that exact file and uploads only when they just printed `CLEAN` (or `NO-LIST`), `OCR-CLEAN`, `PATTERN-CLEAN` and `VIEW-MATCH`. `command -v tesseract >/dev/null || echo NO-OCR` comes first; `NO-OCR` means no upload in 1.4.0.
7. **When uploads happen:** at the Stop gate, before the decision comment, private repos only. On a PUBLIC repo nothing is uploaded; at the end of the run the pictures move to `~/.superfix/journal/<owner>-<repo>/pictures/<key>/` (the run folder is deleted at the end), and the decision comment gives that `~/...` path.
8. **The `assets` release:** created once per repo with `--latest=false` (title "Asset host"). In a repo whose owner is not the signed-in user (`gh api user -q .login`), creating it needs a yes: it adds a tag and can fire release workflows. The decision message then carries the question "May I create a release named assets in <repo> to hold the pictures? (no unless you say yes)" just before the create-issue question; pictures stay local until yes.
9. **Leak handling adds:** `gh release delete-asset assets <file> --repo <o>/<r> --yes`, then tell the owner, and re-check the issue body and comments for the image link.
10. **Qik draft pages** are behind a login: the script path can use a saved login `~/.superfix/auth/<host>.json` (session cookies, a credential: mode 600, never in a repo, never printed or posted). Without it: no Qik picture; Not tested says "needs a one-time saved login". Credentials stay in 1Password, never typed into chat.

### D5. Hosting and the phone
- Standing `assets` release, plain links: `![<caption>](https://github.com/<owner>/<repo>/releases/download/assets/<file>)`, exactly as `thedanielmay/pullstruder` does.
- The GitHub app does not show them, so there is no phone gate; instead the captions carry the meaning and every comment with pictures has the "Pictures show on the website, not in the GitHub app: <issue link>" line.

### D6. The deeper write-up, scaled by tier
- **Template fields the model must fill** (1.3.0 found fields beat side rules):
  - top of body, under the Status line: `Contents: Summary, Problems (P1, P2), Options, Proposed solution, Decision, Done when, Original report`.
  - per problem: In plain words (first), Picture, Failing check, Why it happens (numbered steps, each with the file:line or output that shows it), the 1.3.1 Cause row, Ruled out, Siblings, Viewed (AI detail only), After (filled at close).
  - per option: what changes, good, cost or risk, effort.
  - new `## Proposed solution` per problem: numbered steps; What will look different afterwards; What could go wrong (how I would notice); Will stay untested.

| Field | Simple | Moderate | Complex |
|---|---|---|---|
| In plain words | 1 to 2 sentences | up to 4 | up to 4, plus who is affected |
| Why it happens | up to 3 steps | up to 6 | up to 8 |
| Options | 1, plus "leave it" allowed | 2 or 3 | 2 or 3 |
| Proposed solution | up to 4 steps | up to 8 | up to 12, then point at the plan |

- **Panel limits kept:** callout two lines and never dependent on a picture; Simple decision message stays three lines plus "Go?" with one picture below; comment counts unchanged.
- **Question count:** write the numbered questions first, then the callout. A check prints `COUNT-OK` or `COUNT-MISMATCH`: `grep -cE '^[0-9]+\. ' <comment file>` must equal the number in the callout.
- **Final comment** adds the side-by-side picture per problem (D7), the website line, `Cost: about <n> USD (estimate for a <tier> run; the run cannot read its own bill)` and the undo line.

It is a new image, so it goes through the full upload gate (D4 step 6; its `.side` comes from the before picture's mark).
