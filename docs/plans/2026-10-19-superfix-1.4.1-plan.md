### What you will see
- **Labels.** Yellow `superfix:awaiting-decision` whenever Superfix waits for you (a question, a stop, or a PR ready for your review); green `superfix:approved` while it fixes; none while it diagnoses or when it is done. - **Private gap notes.** When a problem is something Superfix does not cover (a document, a process, a sheet), it writes a short note about that KIND of problem: what a playbook would need. - **Before and after pictures line up.** The after picture uses the same page area as the before picture. If the thing moved out of that area, the after picture is widened and the caption says so.

### The three new required lines (in every decision comment and final comment, AI detail part)
- `Labels:` which Superfix label the issue carries right now, read back from GitHub (or "not set" and why). Lets you trust the label in the saved search.
- `Diagram:` whether diagrams were asked about, drawn, held on your Mac, or skipped, and why.
- `Gap note:` whether this run wrote a note about a kind of problem Superfix does not cover, and where (your private repo, your Mac, or none needed).

## (b) Design decisions, with reasons
### D1. Labels follow the Status line
- **Rule:** a Status value starting "Waiting for you", "Stopped" or "Ready for review" means `superfix:awaiting-decision`; "Fixing" means `superfix:approved`; "Diagnosing" and "Done" mean neither. Every moment in scope already changes the Status line:

| Moment | Status (1.4.0 text) | Label after |
|---|---|---|
| Stop gate | Waiting for you: N questions | awaiting-decision |
| Go, or fast lane | Fixing problem 1 of N | approved |
| Loop back (fix failed twice), panel overturn | Waiting for you: N questions | awaiting-decision |
| Budget stop, blocker | Stopped: <reason> | awaiting-decision |
| Qik waiting for "published", held pictures | Waiting for you to publish / post the pictures? | awaiting-decision |
| PR ready | Ready for review: PR <link> | awaiting-decision |
| Re-diagnose after reply 1 | Diagnosing | none |
| Merged and closed | Done | none |

- Reason: the model follows fields better than lists (1.3.0, 1.4.0), so labels hang on a line it already writes, and `Labels:` is a REQUIRED field in the decision comment, the final comment and the progress, budget-stop, blocker-stop and loop-back message templates.
- **Commands, each printing one word, no `2>/dev/null`:** permission check (`LABELS-OK`, `LABELS-SKIPPED <why>`), ensure (`LABEL-EXISTS`, `LABEL-CREATED`, `LABEL-CREATE-FAILED`), add (`LABEL-ADDED`, `LABEL-ADD-FAILED`), remove (`LABEL-REMOVED`, `LABEL-REMOVE-FAILED`, `LABEL-NOT-PRESENT`), read back (`LABELS-NOW <list>`). Add the new label before removing the old. **Remove only a label the read-back lists**; the command reads back first and never calls `--remove-label` on a label the issue lacks (T1 still records that exit code). The `Labels:` field is copied from `LABELS-NOW`, never typed from memory.
- Existence is checked with `gh api repos/<o>/<r>/labels/<url-encoded name>` before creating, so "already exists" and "no permission" are told apart.
- **When labels are not used** (`LABELS-SKIPPED`, no question, no extra round trip): the signed-in user does not own the repo (`not-owner`); a workflow could react (`workflows`); a create or add failed (`<word>`).
  - The workflow scan is the strict 1.4.0 `assets` scan from evidence.md (every file under `.github/workflows/` at any depth, any case; a file it cannot read is `UNREAD` and counts as a flag; flow-syntax `on: [...]` or `on: {...}` flags), with the label words in place of the release words: any file whose text contains `issues`, `label`, `labeled` or `unlabeled` (any case) flags. Webhooks and GitHub Apps may still react to a label; they cannot be checked from here.
- **One fallback wording everywhere:** the `Labels:` field reads `not set (<word>); marker superfix-awaiting-decision` (or `superfix-approved`). In the issue body the visible text stays plain (the Status line already says "Waiting for you"), and the marker lives in an HTML comment: `**Labels:** not set (<word>) <!-- marker superfix-awaiting-decision -->`. The marker is in the body because the body is current state; a comment would keep matching after the state moved on.
- File-mode journal: `Labels: none (no issue)`.
- Colours: awaiting-decision yellow `FBCA04` "Superfix is waiting for you"; approved green `0E8A16` "Approved; Superfix is working"; gap purple `5319E7` "A kind of problem Superfix does not cover yet" (gap repo only).
- **Restart:** read the Status line, the `**Labels:**` line and the live labels; run the commands so the labels match the Status line.
- **Saved search (README):** the web URL above and `gh search issues --label "superfix:awaiting-decision" --owner thedanielmay --state open`. It misses issues with only the body marker and issues in repos he does not own; README says so. The GitHub app's own filter cannot be tested here.

### D2. Diagrams
- **When asked:** confirmed tier Moderate or Complex, AND the cause or the approved change names 3 or more distinct files, functions or states that interact, AND the problem will be fixed (row Code or Qik). Never Simple, the fast lane or "Everything else" problems. Otherwise `Diagram: NONE (<why>)`.
- **The question, exact:** `<k>. Diagrams: may I add two small diagrams to the issue (the cause today and the change, about <b> boxes each, about 1 USD)? They show on the website, not in the GitHub app. I draw them after your go, so they do not change the options above. (recommended: yes)`. It sits after the problem and budget questions and before the `assets` and create-issue questions (create-issue stays last). His standing rule is to ask before any diagram for GitHub content; this is the ask, and "keep executing" is yes to recommended answers. The budget question now also ends `(recommended: yes)`.
- **The `assets` release:** at the stop, when diagrams will be asked, run the 1.4.0 release check in a dry form (no create). If the only reason it would ask is "no `assets` release yet" on a PRIVATE repo the owner owns with no flagged workflow, the question adds "Yes also lets me create a private image store on this repo." For any other ask-first reason (not owner, tag exists, workflows) the question ends `(no recommendation: <reason in plain words>)` in place of `(recommended: yes)`, so "keep executing" does not cover it.
- **Drawn after go, never before.** At go Superfix writes a brief, one subagent draws, the main thread checks, renders and uploads, then a body update adds them. The fix then proceeds.
- **Information only:** one problem diagram (the chain that causes the failure today, failing part in accent) and one solution diagram (same layout, changed part in accent). At most 9 boxes each, each box a real file, function, step or state from `## Problems`. Drop the solution diagram if it would look the same; say so.
- **Route B only: Superfix follows the skill's files, it does not invoke the skill.** The subagent Reads `SKILL.md`, `references/type-flowchart.md`, `references/style-guide.md` and `assets/template.html` from the installed folder (found by `ls -d "$HOME"/.claude/plugins/cache/diagram-design/diagram-design/*/skills/diagram-design | sort -V | tail -1`, never a hard-coded version). The skill's own "confirm before drawing" rule says to proceed and note the assumptions when the user cannot be reached; a subagent cannot reach him, so it proceeds and writes the assumptions into the AI detail.
  - **Style:** the shipped default tokens. On first use Superfix appends `diagram_style=default (chosen by Claude; change it with diagram-design:profile)` to `~/.superfix/config`; the caption pointer and the AI detail say "default style, chosen by Claude".
  - **Output paths are absolute** (`/Users/<you>/.superfix/runs/<run-key>/diagrams/sf-<N>-diagram-problem.html` and `...-solution.html`, written out in full in the brief), in the per-run folder, never in the clone. A `.diagram-design` marker is never written (it would sit in the clone and break the stop check S1).
  - If the subagent cannot draw without a question, it returns `DIAGRAM-QUESTION <one line>`; nothing is posted; `Diagram: NOT-POSTED (the diagram skill needed an answer)`. The run never ends on the skill's question.
  - **Route C, automatic:** if T1 shows Route B cannot draw non-interactively 3 times out of 3, diagrams are cut from 1.4.1 with no further decision. What stays: labels, gap notes, aligned crops, every required line (`Diagram: NONE (not in this release)` is then dropped from the field list).
- **Safety, every step mechanical:**
  - Source check BEFORE rendering, on the HTML and on a normalised text copy (tags removed so text split across `<tspan>` joins up, HTML entities decoded, zero-width and direction characters removed): the exact-string check and the pattern check (a hit blocks, no "you decide"), the skill's `self_check.py` (no scripts, no remote assets beyond Google Fonts), 1 to 9 `data-sf-node` groups. A grep, not OCR.
  - Render with the BROWSER-SCRIPT interpreter, page scripts off, only `file:` and Google Fonts let through, paper background (a transparent PNG with dark text is unreadable on GitHub's dark theme). Then OCR, the fuzzy secret check and the pattern check on the PNG.
  - Upload only to a PRIVATE repo; any entry in the secrets list holds them (`HELD`; "post the pictures" releases them); public repo or no issue keeps them local.
- **A separate diagram upload command:** the 1.4.0 picture command needs a red or green mark and `VIEW-MATCH`, and its `PICTURES-SAVED` count would count diagrams. Diagrams live in `~/.superfix/runs/<run-key>/diagrams/`, so the 1.4.0 command and count stay byte for byte.
- **The Viewed line for a diagram is a self-report, not a check:** the main thread wrote the brief, so it knows what the diagram should show. The run Reads the PNG and writes `Viewed (self-report): diagram, <what it shows>`; the command only requires that line to exist and be newer than the PNG. What protects a diagram is the source check, OCR and the held rule.
- **Render or check fails:** no diagram, `Diagram: NOT-POSTED (<why>)`, a Not tested line. No `magick` fallback (the 1.4.0 draft): it renders without the fonts.
- **Captions carry the meaning:** `P1 cause today: the CLI, the server and the page each add up the prices themselves; the page skips the third price (orange box).`

### D3. Private gap notes
- **Which problems:** every problem whose Coverage line is "Everything else" (not covered), and a Code or Qik problem whose diagnosis fell to low confidence because its row's own tools were missing (partial; for Qik: the read tools were missing). Qik problems are NOT partial otherwise (decided, k).
- **When:** at the Stop gate, before the decision comment. A write before approval, added to the allowed writes (contradictions 1 to 3).
- **What a note holds: the KIND of problem only.** Title `[gap] <kind of problem>: <generic short name>`. Body: the callout, kind of problem, coverage row, why it stopped at diagnosis, what was tried (tools and steps, generic), what a playbook would need (recognisers, evidence, failing-check form, what done means, tools), confidence, Superfix version. **Never:** a paraphrase or quote of the owner's request, client, repo or person names, paths, URLs, e-mails, code, secrets, pictures or diagrams.
- **Where, and the checks (all must pass, else the note goes to `~/.superfix/gaps/<YYYY-MM-DD>-<slug>.md`, mode 600, `GAP-LOCAL <path>`):**
  - The repo is named by `SUPERFIX_GAP_REPO`, else `gap_repo=` in `~/.superfix/config` (read with `grep`, never `source`, checked against `^[A-Za-z0-9-]+/[A-Za-z0-9._-]+$`). Never hard-coded; never the work repo.
  - (a) visibility `PRIVATE`; (b) the collaborators list is exactly the owner, who is the signed-in user; (c) no GitHub App can read it, and no webhook (`gh api repos/<g>/hooks -q length` is 0).
  - **Check (c) cannot be done mechanically with the `gh` login** (403 and 401 above). So (c) passes only when `~/.superfix/config` has `gap_repo_no_apps=<YYYY-MM-DD>` written by Daniel after he looked at https://github.com/settings/installations, dated within 90 days, plus the webhook count 0. Without that line every note goes to the local file (decided, k). The words: `GAP-REPO-OK`, `GAP-REPO-UNSET`, `GAP-REPO-BAD-NAME`, `GAP-REPO-MISSING`, `GAP-REPO-NOT-OWNED`, `GAP-REPO-NOT-PRIVATE`, `GAP-REPO-SHARED`, `GAP-REPO-HOOKS`, `GAP-REPO-APPS-UNCHECKED`, `GAP-REPO-REFUSED`.
  - The source reference (`repo#number` link) is added to the body ONLY after `GAP-REPO-OK`; a local note gets the run key instead.
- **Redaction before filing (title and body files):** normalise first (HTML entities decoded, zero-width and direction characters removed, lines joined so split text joins up), then the exact-string check and the pattern check extended with `/Users/` paths, e-mail addresses, URLs with a query string and `owner/repo`-looking strings. Any hit: rewrite the note generically and run again; a second hit sends it local. Pattern hits block; no "you decide".
- **De-duplication:** `gh issue list --repo <g> --state open --label superfix:gap --search "<kind> in:title" --limit 10 --json number,title`; a "Seen again" comment (date, run key) only when the kind AND two distinct key words of the title match; otherwise a new note. Local mode: the same rule on `~/.superfix/gaps/` titles. Known limit: search can lag minutes behind a new issue.
- **On the work issue:** the decision comment line gives the count; the note link and the whole-list link `https://github.com/<gap repo>/issues?q=is%3Aopen+sort%3Acomments-desc` only on a PRIVATE work repo; on a PUBLIC work repo "noted in your private gap list" with no link. The final comment's `Gap note:` field adds "open notes in your gap list: <n>" (`gh issue list ... --json number -q length`), or the local count.
- The skill never edits itself because of a note.

### D4. Aligned crops
- Today `shoot` centres the target and cuts the target plus 320 px and 200 px, in viewport terms; `retake` repeats that on the moved target, so the after picture shows a different page area.
- 1.4.1: `shoot` also stores `page_clip` (the clip plus `scrollX`, `scrollY`) and the scroll position in `evidence/<name>.json`. `retake` scrolls back to that position, measures the after target, and:
  - inside the stored area: same area, `CROP-ALIGNED`;
  - partly outside but the union fits in 1280 by 800: the union, `CROP-WIDENED`; `pair` puts the before picture on a union-sized canvas at its offset, grey `#e5e5e5` where nothing was captured; the caption adds "the after side shows a wider area because <target> moved; grey means not in the before picture";
  - union larger than the viewport: the 1.4.0 behaviour, `CROP-DIFFERENT`, and the caption says the sides show different areas.
- No `full_page=True` for the large case: the marks are `position:fixed` and a full-page shot moves them. The MCP path keeps 1.4.0 behaviour (Not tested).
