# Plan: superfix 1.3.0 (core behaviour: diagnose, stop, fix, prove it)
Written 19 Oct 2026 for Daniel, then for the session that builds it. Epic: [superfix-skill#34](https://github.com/thedanielmay/superfix-skill/issues/34). Cut down from `docs/plans/2026-10-19-superfix-behaviour-plan-DRAFT.md` (753 lines, written against the 1.1.1 single file) using the four-reviewer panel record and the 1.2.0 release record on the epic.

## (a) Summary for Daniel
### What changes for you
- **Superfix stops and asks before it fixes anything.**
  - It first finds what is wrong and proves it with a check that fails. Then it writes the problems, the options and a recommendation on the issue, and waits.
  - You get one message with numbered questions. You answer in one line, for example "1 yes, 2 option two". "Keep executing" counts as yes to every recommendation.
- **If you give it a description and no issue**, inside a repo on GitHub, the same message asks whether to create an issue for it.
  - If you say no, the record goes in a file on your Mac, outside the repo, so it never lands in a pull request.
- **It tells you whether it covers your kind of problem**, and quotes the words that made it decide.
  - Code: full diagnose and fix.
  - Qik configuration: diagnose and fix in the draft only, marked as not yet proven by a test. You always publish.
  - Everything else (documents, process, sheets, business): diagnosis only, and it says so plainly.
- **"Fixed" gets a real meaning for code.** The check fails before the fix, passes with it, and fails again when the fix is taken out for a moment. All three results go on the issue.
- **It has a budget you approve**, in plain words, for example "Up to 2 hours, touching these 3 files. I stop and ask if I go over."
- **If its fix fails twice, it stops** and says its diagnosis was wrong, instead of trying a third theory on its own.
- **Passwords and tokens stay out of GitHub.** It keeps a list of every credential you give it in the session and checks every post, commit and PR for them before anything leaves your Mac.
  - Please never type a password into an approval. Name the 1Password item instead.
- **Every final report has a "Not tested" list.**

### What you will notice
- **One extra round trip per run: the stop.** One per run, not one per problem. The create-issue question rides in the same message (decision 2 in section (k)).
- **Fewer comments than today.** A Simple fix posts 2 comments (the decision request, then the result). 1.2.0 posts at least 3 (profile, Phase 1 complete, PR created). A Moderate fix posts 3.
- **The top line of every issue says where things stand**, for example "Waiting for you: 2 questions".
- **Every comment starts with at most two plain lines**: what was done, and what is needed from you.

### What it costs
- **Your time:** one reply per run, usually one line.
- **Run time:** diagnosis adds roughly 5 to 15 minutes on Simple work and 10 to 30 on Moderate work. Estimate, not measured.
- **Model cost:** 1.2.0 test runs cost 0.37 to 0.77 USD each (recorded on [superfix-skill#43](https://github.com/thedanielmay/superfix-skill/pull/43)). Diagnosis will add to this; the test suite records the real figure per run.
- **Skill size:** SKILL.md grows from 297 to at most 400 lines, still well under 1.1.1's 501. About 250 new lines go in four reference files read only when a step needs them.
- **Building it:** about 19 tasks, all on one branch, released together. The test suite is about 14 runs, estimated 10 to 25 USD.

## (b) Design decisions, with reasons
### D1. What 1.3.0 is
- **In:** the diagnosis stage and stop gate; the issue body template (status line, `## Problems`, `## Options`, `## Decision`, `## Done when`, `## Original report` preserved); Decision paraphrased with secrets redacted; the solved check for code; a simple budget; a three-row domain table with the coverage check; the create-issue offer; the file-mode journal outside the repo; the Not tested list; four Qik lines.
- **Out:** everything in section (j), for 1.4.0 or later.
- **Already decided by Daniel, not reopened here:** full fix for code and Qik, diagnosis only elsewhere; one skill; hard stop; issue is the contract; fast lane opt-in per run; the skill never edits itself; [superfix-skill#38](https://github.com/thedanielmay/superfix-skill/issues/38) paused.

### D2. Nothing existing is cut
- Every skill, agent, rule and behaviour in 1.2.0 stays, or changes for a reason named in section (d).
- The diagnosis method **adds to** the exploration-by-type skills in `references/explore.md`. They now run as evidence collectors inside the method.
  - `superpowers:systematic-debugging` stays as the first bug tool. The draft dropped it; this plan keeps it and stops it before its Phase 4 (Implementation).
  - `diagnose` stays as the escalation. It stops before its Phase 4 (Instrument), because Phases 4 to 6 write files.
- New diagnosis tools (Explore fallback, general-purpose report-only agent, episodic memory, Playwright, Qik read tools) go in the new `references/diagnose.md`. The inventory table is not trimmed.

### D3. Phase layout
| Phase | 1.2.0 | 1.3.0 |
|---|---|---|
| 0 | Problem Profile | Intake, coverage check, Problem Profile (no comment posted yet) |
| 1 | Explore | Explore and diagnose. Ends at the **Stop gate** |
| 2 | Design and plan (Moderate, Complex) | unchanged, runs after approval |
| 3 | Execute | unchanged chains, plus budget and solved check |
| 4 | Close | CI watch before the final comment; Not tested list |

- The stop sits after diagnosis and before planning, so the plan is written against an approved option.
- If the expert panel overturns the chosen option or breaks the budget, Superfix goes back to Daniel with one batched message. It never carries on quietly.

### D4. The issue body is the contract and the evidence note
- `## Problems` is written at the end of Phase 1 for every tier. It is the evidence note that fixes three dangling references from the first panel (must-fix 4):
  - "Record baseline numbers in context file" (explore.md) points at a file created in Phase 2.
  - "Verification re-runs the Phase 1 repro" (execute.md) means nothing for non-bug types.
  - "the plan file's task checkboxes" (restart rule) do not exist for Simple work.
- All three now point at `## Problems` (and `## Decision` for restart). The context file stays for Moderate and Complex and copies the evidence from `## Problems`.

### D5. Writes allowed before approval
- Allowed: the journal (issue body, the one decision comment, or the file-mode journal); a scratch folder outside the repo; a detached worktree inside that scratch folder, removed before the stop.
- Not allowed: a branch, any edit to a tracked file, any Qik write, any change to org data, roles or permissions.
- Reason: "confirmed" needs a discriminating test, and some tests need a probe. The probe goes somewhere disposable.

### D6. File-mode journal lives outside the repo
- Path: `~/.superfix/journal/<owner>-<repo>/<YYYY-MM-DD>-<slug>.md` (or `<folder-name>` when there is no remote). Decision 4 in (k).
- Reason: the scope critic found that a journal inside the repo either breaks the `git status --porcelain` check or gets committed into the PR. Outside the repo, neither happens, and the existing branch block stays unchanged.
- The status line is the file's first line. Comments become dated `### <YYYY-MM-DD HH:MM> <stage>` entries at the end.

### D7. Mechanical stops, brief files, fallbacks
- **Stops are counted, not judged.** The panel found the model will call a new cause "the same" or "different" to suit itself, and will reuse the step-1 check as proof.
  - Two failed run-2 attempts stop the run, whatever cause is given (C9).
  - "Confirmed" fills a row (test, what each hypothesis predicts, observed) using a test other than the step-1 check (C4).
  - Budget is measured by commands from `approval-sha`; a fix subagent returns the literal text `BUDGET STOP` (C8).
- **Agents get `references/briefs.md` by absolute path** (C14), because they never load SKILL.md, so rules kept inline there are invisible to them. Review agents get "Report only" because `pr-review-toolkit` agents have the Edit tool.
- **Missing tools fall back, never block**, in this order: the named skill or agent; the built-in `Explore` agent; a `general-purpose` subagent with the report-only header; inline. `## Problems` records `Tools used:`, for example `Tools used: Explore (for feature-dev:code-explorer, missing), systematic-debugging phases 1 to 3, git log. Missing: Playwright.`

### C4. Diagnosis method (`references/diagnose.md`, new)
```
1. Failing check first. Before any theory, run one check that fails on the
   reported symptom (test, command, curl, page check, Qik read-back, measured
   timing). Paste its output. For a feature, the check is the acceptance
   check that fails because the feature is absent. No failing check, no
   hypotheses.
2. Facts apart from inferences. List what was observed, each with the command
   or tool that showed it, separately from what you infer.
3. Differential. Write 3 to 5 ranked hypotheses. Each has a prediction that
   would prove it wrong. Test the cheapest discriminating prediction first.
   Keep "Ruled out, how" for each rejected one.
4. Confirmed means a filled row, using a test that is NOT the step-1 check:
   | Test | H1 predicts | H2 predicts | H3 predicts | Observed |
   Only the hypothesis whose prediction matches the observation is confirmed.
   Anything less is "suspected".
5. Siblings. Once confirmed, search for the same cause elsewhere (other
   callers, sections, forms). List each one found.
6. Scope. Diagnose only problems that explain the reported symptom. Anything
   else goes under "Seen, not diagnosed", one line each.
7. Self-audit before the stop. For each claim in ## Problems: was evidence
   skipped, misread, or missing? Fix it or downgrade to "suspected".

Stop rules, whichever comes first:
- Cause confirmed by a filled row: go to the Stop gate.
- 3 hypotheses falsified and none left that fits: go to the Stop gate with
  what was ruled out, and ask for a new lead.
- About 30 minutes, or 3 attempts at a feedback loop, without a failing check:
  go to the Stop gate and ask for the environment, account, data or file needed.
The 30 minutes covers the whole diagnosis. The 5-minute cap on the Explore
lookup in explore.md is one step inside it.

Existing skills, with their limits:
- systematic-debugging: Phases 1 to 3 only. Its Phase 4 (Implementation) waits
  for approval.
- diagnose: Phases 1 to 3 only. Its Phases 4 to 6 write files; never before
  approval. Its "don't block" rule is overridden by the Stop gate.
- Every other skill in explore.md: as listed there.

Already fixed: if the failing check cannot fail on current main, the escape
hatch in SKILL.md applies; it becomes question 1 of the decision message.
```

Tools and fallbacks table in `diagnose.md` (additions, nothing removed elsewhere):

Fan-out (in `diagnose.md`; brief text in `briefs.md`):

```
Moderate and Complex, or Simple when the first hypotheses do not separate:
dispatch 3 to 4 read-only agents in one message, each with the fan-out brief
from briefs.md (absolute path in the dispatch). Each gets the symptom in the
reporter's words with any stated cause removed, the evidence so far, and the
files or objects in scope. Never the context file, never the owner's guess,
never your leading hypothesis. One agent argues for the strongest cause that
is NOT the leading hypothesis. Agents that read the same files and agree count
as one source. Afterwards run `git status --porcelain`; any change means an
agent broke the rule: revert it and say so in the decision message.
```

### C5. Stop gate (inline, new, end of Phase 1)
```
## Stop gate

Every tier, every run, unless the fast lane was asked for in this run.

1. ## Problems, ## Options and ## Done when are written (journal.md template).
   The ## Done when section quotes the owner's own description of the problem (redacted):
   that is the acceptance criterion.
2. Status line: "Waiting for you: <N> questions".
3. Run the redaction check (below), then post ONE decision comment, or write
   it to the file-mode journal. It holds every question for this run,
   numbered, each with the recommended answer, the effort and the budget.
   Simple with one problem: three lines (problem, fix, effort) and "Go?".
4. Say the same in chat and END THE TURN. Do not create a branch, edit a
   tracked file, write to Qik, read references/execute.md or
   references/briefs.md, or start any Phase 2 or 3 step until a go arrives.

Go: "yes", "go", "1 yes, 2 option two", "keep going", "keep executing", "do
it", or any reply that answers every question. "Keep going" style replies
accept every recommendation. A reply that answers only some questions: ask
only the rest. Anything else (a question, a new fact): answer it, update the
record, stay stopped.

On go: write ## Decision (below) as a body update, no comment. Record
approval-sha = `git rev-parse origin/<default-branch>` and the approval time.
Status "Fixing problem 1 of <N>".

Fast lane: only when THIS run's request says so ("just fix it", "don't
wait"). Only for one problem, Simple tier, row Code, type not security.
Still run Phase 1 and write ## Problems; post the decision message as a
notice and continue. Otherwise say in one line why it does not apply, and stop.
```

Decision message template (in `journal.md`, the callout line is inline):

```
> **In plain English:** I found 2 problems and what causes them. I need 2 answers before I fix anything.

Reply in one line, for example "1 yes, 2 option two". "Keep executing" means yes to all my recommendations.

1. P1 (problem 1: the total is off by one): fix the loop bound (recommended) or rewrite total()? About 20 minutes of my time; your part: reply once.
2. Budget: Up to 1 hour, touching these 2 files: sum.js, test/sum.test.js. I stop and ask if I go over. OK?

---
<AI detail: Coverage block, Problem Profile, Tools used, failing check output, hypotheses table>
```

- Effort wording, exact form: "About 1 hour of my time; your part: publish once." (Qik) or "...your part: reply once." (code).
- When the work needs a login, add one line: "Please don't type passwords here. Name the 1Password item instead."
- First mention of any P number in a message reads "P1 (problem 1: <short name>)".

### C7. Redaction detail (`references/redaction.md`, new)
```
Session list: every exact string the owner gave as a credential, plus any found
in tool output. Keep it in a file made with `umask 077; mktemp` outside the
repo; delete it at the end of the run.

Exact-string check (catches a password with no keyword):
  git diff origin/<base>...HEAD > "$T/diff"; git log --format=%B origin/<base>..HEAD > "$T/msgs"
  grep -F -n -f "$SECRETS" "$T/diff" "$T/msgs" <each body file> && echo BLOCKED

Pattern check (report each hit, then decide):
- keyword forms only: (password|passwd|pwd|secret|token|api[_-]?key|auth|
  bearer|cookie|session)\s*[:=]\s*\S+   (any case)
- prefixes: sk-, ghp_, gho_, github_pat_, AKIA[0-9A-Z]{16}, eyJ<...>.<...>.,
  -----BEGIN <...> KEY-----, ://<user>:<pass>@
- long runs: 32 or more mixed letters and digits with no spaces
Allowlist, never redacted:
- 40-hex strings, and any string `git cat-file -e <s>` resolves (git SHAs)
- 24-hex strings next to `_id` or `/goto/` (Qik record ids)
- 64-hex strings next to `sha256`
Not allowlisted and unsure: redact. Replace with [redacted].

Repo visibility: before creating an issue from chat text, run
`gh repo view --json visibility -q .visibility`. PUBLIC: show the exact text in
the decision message and wait for yes.

Leak handling: comment: `gh api -X DELETE repos/<o>/<r>/issues/comments/<id>`.
Issue body: rewrite it, then tell the owner the old text stays in the edit
history until they delete that revision in the GitHub page. Commit not pushed:
amend or rebase before pushing. Pushed: tell the owner, rotate first.
```

### C8. Budget (inline, Phase 3)
```
### Budget

Proposed in the decision message, fixed at approval. Defaults:
  Simple:   6 commits, 2 hours, the files named in ## Options plus their tests
  Moderate: 15 commits, 4 hours, the files in the plan plus their tests
  Complex:  as stated in the plan
Plain wording: "Up to 2 hours, touching these 3 files. I stop and ask if I go over."

Measure before every commit (main thread or fix agent):
  commits: git rev-list --count <approval-sha>..HEAD -- . ':(exclude)docs/superpowers/plans'
  files:   git diff --name-only <approval-sha>...HEAD   (any file not named = over)
  time:    date, minus the approval time in ## Decision
  Qik:     draft writes made as part of the fix (writes made only to verify do not count)
The journal is outside the repo, and plan commits are excluded, so neither counts.
Over any limit: stop. A fix agent returns a message whose first line is exactly
BUDGET STOP; the main thread posts it (callout first), sets the status line to
"Stopped: over budget (<which>)" and ends the turn. Offer: 1 extend, 2 cut
scope, 3 stop. Never continue past a limit on your own.
Max 2 review passes and max 2 expert panel passes are unchanged.
```

### C9. Solved check for code (inline, Phase 3 verification)
```
### Solved check

"Solved" means three runs, each recorded with output in the final comment:
  Run 1, base fails:   the failing check from ## Problems, on approval-sha.
  Run 2, fix passes:   the same check on the branch.
  Run 3, revert fails: in a scratch worktree of HEAD, reverse-apply the
     non-test part of `git diff <approval-sha>...HEAD`, run the check, expect
     failure, remove the worktree. The branch is never touched.
Run 2 must also show the owner's description quoted in ## Done when no longer
holds.
If run 3 passes, the check does not detect the problem: fix the check, not the
code, and re-run all three.
When run 3 does not apply, say why in one line and put it under Not tested:
  - refactor meant to keep behaviour: no failing check exists; full suite
    passes before and after instead
  - new feature whose check cannot run without it: run 3 fails by import or
    missing command; record that, it still counts
Two failed run-2 attempts, whatever the cause given: stop. Post:
  "My fix failed twice, so my diagnosis was wrong. Work kept on the branch.
   Used 1h10 of 2h. 1 re-diagnose (about 20 min), 2 stop."
Status "Waiting for you: 1 question". Never re-diagnose quietly.
```

### D-2. Mechanical preservation check
Script at `tests/preservation-check.py` in the worktree (not loaded at runtime). Justifications at `tests/preservation-1.3.0.md`, one line per removed or changed 1.2.0 line: `- <exact old line> :: <manifest row name>`.

```python
#!/usr/bin/env python3
"""List every non-blank 1.2.0 line missing from 1.3.0; fail on unjustified ones."""
import pathlib, subprocess, sys
ROOT = pathlib.Path(sys.argv[1])            # worktree root
FILES = ["skills/superfix/SKILL.md"] + [f"skills/superfix/references/{n}.md"
         for n in ("journal", "explore", "execute", "inventory")]
def old(path):
    return subprocess.run(["git", "-C", str(ROOT), "show", f"v1.2.0:{path}"],
                          capture_output=True, text=True, check=True).stdout
new = set()
for p in (ROOT / "skills/superfix").rglob("*.md"):
    new |= {l.strip() for l in p.read_text().splitlines() if l.strip()}
just = set()
for l in (ROOT / "tests/preservation-1.3.0.md").read_text().splitlines():
    if l.startswith("- ") and " :: " in l:
        just.add(l[2:].rsplit(" :: ", 1)[0].strip())
bad = 0
for f in FILES:
    for i, l in enumerate(old(f).splitlines(), 1):
        s = l.strip()
        if s and s not in new:
            tag = "justified" if s in just else "UNJUSTIFIED"
            bad += tag == "UNJUSTIFIED"
            print(f"{tag}\t{f}:{i}\t{s}")
print(f"{bad} unjustified"); sys.exit(1 if bad else 0)
```
